# 플랫폼 사용자 개인화 설계 및 구현 공수 산정

## 1. 개요
플랫폼 내 여러 화면에서 사용자별 개인화 설정을 저장하고, 저장된 상태를 화면 렌더링 시 반영하기 위한 백엔드 설계/구현 산정이다.

### 범위
- 사용자 개인화 항목(확장 예정)
  - 대시보드 하단 위젯: 위젯 순서/표시 여부
  - 대시보드 상단 ticker setting: 체크된 ticker만 조회
  - Topic Tracker: 사용자별 토픽 추가/삭제/트래킹 on/off

### 공통 가정
- 인증된 사용자 기준 `userNo`(`usr_no`)로 개인화 상태 저장
- Spring Boot + MyBatis 기반 서비스
- 관계형 DB(MySQL/PostgreSQL) 사용
- 배포 파이프라인은 기존 운영 체계를 사용
- 테스트: 현재 `build.gradle`에서 테스트 비활성화(`test { enabled = false }`) 상태이므로 운영 반영 전 테스트 정책 재설정 필요
- 본 산정은 백엔드 구현 중심(프런트/디자인/배포 운영 상세 제외)

## 2. 공통 설계 (항목 공통 기반)
| 항목 | 공수(MD) | 설명 |
|---|---:|---|
| 개인화 도메인 모델/ERD 정의 | 1.0 | 사용자 개인화 핵심 엔티티 및 관계 정의 |
| API 스펙 정의 | 0.8 | 요청/응답/에러코드/권한 |
| 영속성 전략 설계 | 1.0 | 공통 저장 전략(확장성/조회 효율/정합성) |
| 마이그레이션/인덱스/제약 정책 | 0.8 | DDL, 인덱스, 유니크/외래키 정책 |
| 공통 유효성/중복/에러 정책 | 0.7 | 입력 검증, 중복 등록 방지, 삭제/변경 정책 |
| 테스트 전략 및 시나리오 정의 | 0.7 | 항목별/통합 테스트 조건 정리 |

**공통 설계 합계: 5.0 MD**

## 3. 항목별 백엔드 구현 산정

### A. 대시보드 하단 위젯 개인화

- 범위
  - 사용자 위젯 목록 조회
  - 표시 여부 토글
  - 위젯 순서 변경(순번 저장)

- 구현 산정

| 항목 | 공수(MD) | 설명 |
|---|---:|---|
| 위젯 선호치 스키마/Mapper/DTO | 1.0 | 사용자-위젯 설정 저장 |
| 조회/저장/순서 변경 API | 1.5 | CRUD + 순번 동기화 |
| 검증 및 충돌 방지 로직 | 0.7 | 중복/범위/순번 충돌 처리 |
| 기본값/신규 사용자 처리 | 0.3 | 기본 위젯 세트 제공 |
| 단위/통합 테스트 | 1.0 | 주요 시나리오 반영 |

**합계: 4.0 MD**

### B. 대시보드 상단 ticker setting

- 범위
  - 사용자가 체크한 ticker 저장
  - 체크된 ticker만 조회 응답에 반영
  - 기본 체크 목록 제공(신규 사용자 초기값)

- 구현 산정

| 항목 | 공수(MD) | 설명 |
|---|---:|---|
| ticker 개인화 스키마/Mapper/DTO | 1.0 | 사용자별 다건 ticker 설정 |
| 추가/삭제/체크 상태 변경 API | 1.2 | 일괄/단건 처리 지원 |
| 조회 API 연동 및 필터링 | 1.0 | 기존 조회 로직과 결합 |
| 동시성/중복/미존재 처리 | 0.8 | 동시 변경 및 무효값 차단 |
| 테스트 | 1.5 | 조회/필터/변경 시나리오 |

**합계: 4.5 MD**

### C. Topic Tracker (토픽 트래킹)

- 범위
  - 사용자별 토픽 추가
  - 사용자별 토픽 삭제
  - 트래킹 on/off 토글
  - 사용자 토픽 목록 조회

- 구현 산정

| 항목 | 공수(MD) | 설명 |
|---|---:|---|
| 사용자-토픽 맵핑 스키마/Mapper/DTO | 1.2 | 유니크 제약 기반 중복 방지 |
| 추가/삭제/토글 API | 1.5 | 상태/권한 검증 포함 |
| 비즈니스 유효성 처리 | 0.8 | 미존재 토픽/권한 제한 등 |
| 테스트 | 1.0 | 토픽 상태변경/삭제/조회 |
| 부가 정책(기본 토픽/노출) | 0.5 | 기본값 및 fallback 정책 |

**합계: 5.0 MD**

## 5. 총량

- 공통 설계: **5.0 MD**
- 항목별 구현: **13.5 MD** (4.0 + 4.5 + 5.0)
- 공통 후작업: **3.3 MD**

**총합: 21.8 MD**

보수적으로 산정하면 **21~23 MD** 범위 권장.

## 6. 일정 예시(1인 기준)

- 1주차: 공통 설계 + 위젯 구현
- 2주차: ticker 구현 + Topic Tracker 착수
- 3주차: Topic Tracker 완료 + 통합 테스트/문서화

## 7. MD(Unit) 안내

`MD`는 **Man-Day(인력일)**이며, 1 MD는 일반적으로 1인당 1일(약 8시간) 작업량을 의미한다. 

예: 21.8 MD / 2명 투입 시는 업무 병렬도를 감안해 대략 11~12 인력일(실효 2주 내외) 정도로 환산 가능.

## 8. 확장성 고려사항

- 개인화 항목이 계속 추가되는 점을 고려해 공통 메타테이블 패턴 또는 JSON 기반 설정 저장 테이블 확장 전략을 함께 검토
- `usr_no`, `feature_code`, `target_id`, `sort_order`, `is_visible`, `is_tracked` 등의 공통 필드를 최소 공통 스키마로 정리
- 이벤트 기반 동기화가 필요한 경우(예: 설정 즉시 반영) 캐시 전략과 무효화 정책을 별도 설계
